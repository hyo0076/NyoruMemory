# 병렬 처리와 오류 청크 건너뛰기

2026-10-09 · `codex/jev-memory-shadow` 로컬 변경

## 사용 방법

- 설치 파일: `dist/experimental/NyoruMemory-jev-shadow.js`
- **나눠 정리하기 → 최대 동시 요청 수**를 설정한다. 독립된 종류별 작업에 적용하며 사실·관계 묶음 갱신도 같은 설정을 사용한다. 필요한 종류가 두 개면 두 개만 호출한다.
- **남은 대화 모두 기억하기**는 시작 시점의 남은 구간을 끝까지 진행한다. 이미 실패한 청크와 새로 실패한 청크는 그대로 보관하고 건너뛴다. 성공한 뒤쪽 청크는 즉시 저장한다.
- 끝나면 저장한 청크 수와 실패 구간 목록을 보여준다. 각 구간에서 **오류 위치 / 빠른 복구**, **이 청크 재시도**를 사용할 수 있다. 실패 목록은 처리 기록에도 남는다.
- 취소, 채팅 변경, 원문 변경, 인증/권한/요금/주소 오류 및 호출 제한은 다음 요청을 계속 보내지 않고 이유를 표시한다. 일반 자동 정리의 실패 중지 동작은 유지한다.

## 병렬 처리 변경

- API 요청 전 선택적인 진단 기록 저장을 기다리지 않는다. 진단 변경은 잠깐 모아서 쓰고, 내보낼 때는 대기 중인 기록까지 반영한다.
- 기기 저장소의 복구·진단 자료는 기록별로 읽고 쓴다. 상태 목록만 확인할 때는 원문과 응답 전체를 읽지 않는다. 기존 배열은 처음 수정할 때 옮겨 읽는다. 기존 저장소 호환 경로도 유지한다.
- 원문은 이미 저장된 청크를 참조한다. 각 요청에는 그 작업의 지침과 입력, 원본 응답을 보관한다. 응답은 파싱 전에 필수 복구 저장을 마친다.
- 성공한 요청의 보관 이력은 제한 안에서 정리하지만, 아직 해결하지 않은 실패 응답은 후속 성공 기록 때문에 밀어내지 않는다. 기기의 실제 저장 공간 부족은 오류로 표시한다.
- 진행창의 **API 응답 대기 / 최대 요청 수**는 API를 보낸 뒤 본문을 받기까지의 개수다. 요청 준비, 응답 보관, 결과 확인은 따로 표시한다. 이는 서버 내부의 모델 실행 개수를 뜻하지 않는다.
- 진단에는 전송/수신 시각, 요청 준비 시간, 응답 대기 시간, 응답 보관 시간이 남는다.
- 임베딩은 모델당 두 묶음, 플러그인 전체 네 요청까지 병렬화한다. 기존 벡터 재사용과 모델별 저장 분리, 취소·기억 revision 확인은 유지한다.

## 실패 구간과 기억 보호

- 처리 구간에 빈 곳이 있어도 성공한 구간을 중복 생성하지 않는다. 미처리 메시지 수와 용량은 아직 저장되지 않은 구간만 센다.
- 실패 구간은 처리 완료로 표시하지 않으며, 해당 원문을 기억으로 대체하지 않는다.
- 나중에 앞쪽 실패를 복구할 때 이미 저장된 최신 사실·관계를 과거 상태로 되돌리지 않는다. 원래 성공한 종류별 초안은 원문·지침·모델·기준 기억이 호환될 때 재사용한다.
- 호환 판정에서 생략할 수 있는 차이는 해당 실패 구간보다 뒤에 새로 저장된 AI 청크뿐이다. 기존 기억 편집, 무효화, 원문/지침/모델 변경은 여전히 구분한다. 적용 직전의 원문·채팅·revision·중복 구간 검사도 유지한다.
- 중간 실패를 허용하는 상태 버전은 12다. 기존 버전 11까지 읽고, 쓰기 전에 기존 상태를 `before-v12`에 보관한다. 기억을 초기화하거나 재추출하는 변경은 아니다.

## 실행 범위

사용자 지시에 따라 테스트, 설치된 RisuAI 실행 확인, 실제 모델 API 호출과 GitHub 업로드는 하지 않는다. 설치 파일 빌드만 수행한다. 속도 개선 배율은 측정하지 않았다.
